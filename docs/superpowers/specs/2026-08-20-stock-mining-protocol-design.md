# DWELL — дизайн-спецификация

**Дата:** 2026-08-20
**Статус:** утверждён, готов к планированию реализации
**Сеть:** Robinhood Chain (chainId 4663)
**Актив награды:** TSLA — `0x322F0929c4625eD5bAd873c95208D54E1c003b2d`

## Название

**DWELL.** От `dwell time` — термина веб-аналитики, означающего время, проведённое пользователем на странице. Протокол измеряет буквально эту величину, поэтому имя описывает механику, а не украшает её.

Тикер токена: `$DWELL`.

---

## 1. Что строим

Протокол «майнинга акций»: держатель токена проекта открывает вкладку с дашбордом, держит её видимой и получает награду в токенизированной акции Tesla. Доля пропорциональна произведению баланса на активное время.

Источник наград — creator-комиссии лаунчпада с торгового оборота токена проекта, конвертируемые в TSLA.

Прототипом послужил stockmachine.cash. Мы воспроизводим механику, но заменяем экономику распределения (§4) и радикально сокращаем объём.

## 3. Архитектура

```
ОНЧЕЙН
  RewardVault.sol           единственный свой контракт
  Токен проекта             типовой контракт лаунчпада
  Своп                      Uniswap v3: ETH -> WETH -> TSLA (тир 0.3%)

ВОРКЕР (внутри процесса API)
  каждые 5 мин              веса -> дрип -> кумулятивы -> корень -> publishRoot
  по порогу                 ETH с коллектора -> обернуть -> своп -> TSLA в вольт

API (один процесс)
  POST /session             подпись кошелька -> токен сессии
  POST /heartbeat           раз в 10 с, пока вкладка видима
  GET  /me                  балансы, вес, клеймабл + Merkle-пруф
  GET  /stats               публичные метрики

ХРАНИЛИЩЕ
  SQLite через встроенный node:sqlite
```

### Закреплённые адреса

Установлены разбором реальных транзакций в сети, не предположением. Все идут в код константами и никогда не резолвятся динамически.

| Что | Адрес |
|---|---|
| TSLA | `0x322F0929c4625eD5bAd873c95208D54E1c003b2d` |
| WETH | `0x0Bd7D308f8E1639FAb988df18A8011f41EAcAD73` |
| SwapRouter02 | `0xCaf681a66D020601342297493863E78C959E5cb2` |
| UniswapV3Factory | `0x1f7d7550B1b028f7571E69A784071F0205FD2EfA` |
| Пул WETH/TSLA 0.3% | `0xA953CA88ff430e9487c60cA34d757414f4efdA07` |
| Multicall3 | `0xcA11bde05977b3631167028862bE2a173976CA11` |

Фабрика Uniswap v3 в этой сети развёрнута **не по каноническому адресу**, поэтому её нельзя брать из памяти или документации — только отсюда.

**Публичный RPC — не архивный.** Замерено: историческое состояние живёт от 6000 до 8000 блоков, при блоке в ~100 мс это всего 10–13 минут. Отсюда жёсткое требование к воркеру: закрытие бакетов обязано держаться у головы цепи. Если воркер отстал сильнее окна, балансы тех бакетов уже не восстановить — их следует пропустить, а не дозаполнять текущими значениями, иначе продавший в простое майнер получит вознаграждение за баланс, которого у него не было.

### Чистые функции (без I/O)

Вся денежная логика изолирована в детерминированные функции без обращений к сети и базе. Это даёт полное покрытие тестами и бесплатное восстановление после сбоя (§7.4).

- `epoch-clock` — `epochOf(ts)`, `bucketOf(ts)`, границы эпохи
- `settlement` — `(evidence, vaultState) -> allocations`

### Границы доверия

| Ключ | Где живёт | Может | Не может |
|---|---|---|---|
| KEEPER | горячий, на сервере | публиковать корни, свопать комиссии | трогать средства вольта |
| ADMIN | холодный, аппаратный | pause, смена кипера, потолок, вывод излишка | вывести начисленное другим |

Компрометация кипера даёт злой корень, но ущерб ограничен потолком на корень, инвариантом платёжеспособности и задержкой перед клеймом.

## 4. Экономика

### Проблема прототипа

Прототип держит 0% резерва: вся собранная ETH немедленно конвертируется и немедленно раздаётся майнерам той эпохи, в которую попала. Оборот мемкоина рваный, поэтому награда скачет, а при падении оборота обнуляется в тот же день. Замеренный результат — 0 активных майнеров на восьмой день.

### Решение: дрип из резерва

Покупка происходит сразу (обещание «комиссии становятся акциями» выполняется буквально). Сглаживается **распределение**.

```
unallocated = TSLA.balanceOf(vault) - (totalAllocated - totalClaimed)
release     = unallocated * r
share(a)    = release * weight(a) / totalWeight
```

При `totalWeight == 0` релиз не происходит — резерв остаётся нетронутым.

### Параметр

Задаётся через период полураспада — за сколько дней резерв уменьшится вдвое при нулевом притоке.

```
H = 3 дня
r = 1 - 0.5^(1/864) = 8.019e-4 за эпоху
  = 20.63% в сутки
```

Резерв держим в TSLA, а не в ETH: вольт должен людям TSLA, поэтому и резерв должен быть в TSLA — иначе между сбором и раздачей возникает валютный риск.

### Свойства

- Никогда не обнуляется — раздаётся доля, а не сумма.
- В равновесии выплата равна притоку: `R* = X / p = 4.85` дневных притоков. Буфер не уменьшает суммарные выплаты, только сглаживает их.
- При смерти оборота машина затухает неделями, а не встаёт за день.

### Предзаряд вольта

Стартовать с пустым вольтом нельзя: дрип сначала копит подушку и недоплачивает именно в первые дни, когда внимание пиковое.

```
Приток 5 TSLA/день, старт с нуля, выплаты по дням:
H=3:   1.03 -> 1.85 -> 2.50 -> 3.02 -> 3.43 -> 3.75 -> 4.01
```

Поэтому вольт заряжается TSLA до запуска. Это не расход, а сдвиг во времени.

## 5. Ядро сеттлмента

### Часы

```
EPOCH_SECONDS  = 300     epoch  = floor(unix / 300)
BUCKET_SECONDS = 10      bucket = floor(unix / 10)
                         30 бакетов в эпохе
```

### Приём хартбитов

Запись двухфазная:

1. **На приём хартбита** — вставка `(account, bucket_id)` с пустым балансом. Идемпотентно: повторный хартбит в тот же бакет не создаёт второй строки и не является ошибкой.
2. **На закрытии бакета** — один multicall читает балансы всех отметившихся аккаунтов на зафиксированном блоке, строки заполняются `block_number` и `balance`.

Баланс намеренно читается не на каждый хартбит: один RPC-вызов на бакет вместо N, и снимок получается консистентным.

`balance < MIN_BALANCE` -> строка остаётся, вес нулевой.

Итоговая запись: `(account, bucket_id, block_number, balance)`.

### Вес

```
weight(a, e) = sum over active buckets b of balance(a, b)
```

Сумма по бакетам, а не «баланс × число бакетов» — корректно учитывает изменение баланса в середине эпохи.

### Арифметика

Всё на BigInt с округлением вниз. Остаток от округления не аллоцируется и остаётся в `unallocated`, то есть достаётся следующим эпохам. Пыль не теряется никогда.

### Дерево

```
leaf = keccak256(bytes.concat(keccak256(abi.encode(account, cumulative))))
```

Двойное хеширование листа и сортировка пар — стандарт OpenZeppelin/Uniswap, закрывает подмену листа узлом. Проверка на контракте — `MerkleProof.verify`.

Клейм кумулятивный: `к выплате = cumulative - уже_заклеймлено`. Один пруф покрывает всю историю аккаунта.

### Скрытие ожидаемых наград

Личные незавершённые начисления не показываются. Видна только финализированная сумма после публикации корня. Это снимает класс конфликтов при коррекциях — прототип на этом обжёгся (в его манифесте зафиксирован инцидент с 29 переплаченными аккаунтами).

## 6. Контракт RewardVault.sol

Иммутабельный. Без прокси. Всё, что можно взять из OpenZeppelin, берётся из OpenZeppelin.

### Состояние

```solidity
IERC20  public immutable rewardToken;      // TSLA, вшит при деплое
uint64  public constant CLAIM_DELAY = 300; // одна эпоха

bytes32 public activeRoot;                 // против него проверяются клеймы
uint64  public activeThroughEpoch;

bytes32 public pendingRoot;                // созревает через CLAIM_DELAY
uint64  public pendingThroughEpoch;
uint64  public pendingActivatesAt;

uint256 public totalAllocated;             // по последнему (pending) корню
uint256 public totalClaimed;
uint256 public maxAllocationIncreasePerRoot;
mapping(address => uint256) public claimed;
```

### Два слота корня

Наивная схема «один корень + запрет клейма на CLAIM_DELAY» **не работает**:
корень публикуется раз в 300 с, задержка тоже 300 с, поэтому окно клейма
никогда не открывается. Нужны два слота.

```solidity
function _promoteIfDue() internal {
    if (pendingActivatesAt != 0 && block.timestamp >= pendingActivatesAt) {
        activeRoot = pendingRoot;
        activeThroughEpoch = pendingThroughEpoch;
        pendingActivatesAt = 0;
    }
}
```

Вызывается в начале `publishRoot` и `claim`. Активный корень всегда
отстаёт ровно на одну эпоху — это и есть задержка, но она не блокирует
клеймы.

### publishRoot

```solidity
function publishRoot(uint64 newEpoch, bytes32 newRoot, uint256 newTotalAllocated)
    external onlyRole(KEEPER_ROLE) whenNotPaused
{
    _promoteIfDue();

    if (newEpoch <= pendingThroughEpoch)              revert EpochNotAdvancing();
    if (newTotalAllocated < totalAllocated)           revert AllocationDecreased();
    if (newTotalAllocated - totalAllocated > maxAllocationIncreasePerRoot)
                                                      revert AllocationCapExceeded();
    if (newTotalAllocated > rewardToken.balanceOf(address(this)) + totalClaimed)
                                                      revert Insolvent();

    pendingRoot = newRoot;
    pendingThroughEpoch = newEpoch;
    pendingActivatesAt = uint64(block.timestamp) + CLAIM_DELAY;
    totalAllocated = newTotalAllocated;

    emit RootPublished(newEpoch, newRoot, newTotalAllocated);
}
```

Инвариант платёжеспособности проверяется против `totalAllocated` последнего
корня, а не активного. Это строже и потому безопаснее: кумулятивы
активного корня всегда меньше либо равны кумулятивам последнего.

**Инвариант платёжеспособности.** Содержательная форма:

```
totalAllocated - totalClaimed <= rewardToken.balanceOf(vault)
```

Записан в коде в перенесённом виде. Сравнивать `totalAllocated` с балансом напрямую нельзя — после первых клеймов баланс падает, а `totalAllocated` растёт, и контракт заклинило бы.

### claim

```solidity
function claim(uint256 cumulativeAmount, bytes32[] calldata proof)
    external nonReentrant whenNotPaused
{
    _promoteIfDue();
    if (activeRoot == bytes32(0)) revert ClaimNotOpen();

    bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(msg.sender, cumulativeAmount))));
    if (!MerkleProof.verify(proof, activeRoot, leaf)) revert InvalidProof();

    uint256 already = claimed[msg.sender];
    if (cumulativeAmount <= already) revert NothingToClaim();

    uint256 amount = cumulativeAmount - already;
    claimed[msg.sender] = cumulativeAmount;
    totalClaimed += amount;
    rewardToken.safeTransfer(msg.sender, amount);
    emit Claimed(msg.sender, amount, cumulativeAmount);
}
```

Клеймит только `msg.sender`. Клейма за третье лицо нет.

### Админ

```solidity
setMaxAllocationIncreasePerRoot(uint256)
pause() / unpause()
withdrawSurplus(address to, uint256 amount)            // только сверх обязательств
rescueForeignToken(IERC20 t, address to, uint256 amt)  // require(t != rewardToken)
```

`withdrawSurplus` уважает тот же инвариант: доступно только `balance - (totalAllocated - totalClaimed)`.

### Намеренно отсутствует

Прокси и апгрейды, локи, платные бусты, несколько токенов награды, клейм за третье лицо. Это вырезанная сложность, а не забытая.

## 7. Бэкенд

### 7.1 Процесс

Один Node/TypeScript процесс: HTTP API и воркер вместе, планировщик внутри. Хранилище — SQLite через встроенный `node:sqlite`, поэтому отдельный сервер БД не нужен и зависимостей ноль. Сеттлмент сотни аккаунтов занимает миллисекунды и событийный цикл не блокирует.

При одном процессе и нагрузке порядка десяти записей в секунду SQLite в режиме WAL избыточен по запасу. Переход на Postgres понадобится только при разделении на несколько процессов, чего в объёме v1 нет.

### 7.2 Схема данных

```sql
heartbeats   (account, bucket_id, block_number, balance)  PK(account, bucket_id)
epochs       (epoch, total_weight, release, status)
entitlements (account, cumulative)
roots        (through_epoch, root, tx_hash, published_at) UNIQUE(through_epoch)
purchases    (eth_in, tsla_out, tx_hash, at)
```

`PK(account, bucket_id)` даёт идемпотентность хартбитов на уровне БД. `UNIQUE(through_epoch)` физически не даёт опубликовать эпоху дважды.

Все денежные величины хранятся строками: SQLite оперирует 64-битными целыми, а суммы в wei их переполняют.

Дерево не хранится — перестраивается из `entitlements` за миллисекунды.

### 7.3 Конвертация комиссий

Получатель creator fee лаунчпада — адрес кипера. Путь конвертации установлен разбором реальной покупки прототипа:

```
ETH -> WETH.deposit() -> SwapRouter02.exactInputSingle(WETH -> TSLA, fee 3000) -> перевод в вольт
```

Это Uniswap **v3**, не v4. Нативного пула ETH/TSLA в v4 не существует: там TSLA выступает котируемым активом для лаунчпадных токенов, и свопать против неё ETH не через что.

Тир комиссии пула TSLA — **0.3%**, тогда как у прототипа с NVDA был 0.05%. Лимит проскальзывания обязан это учитывать: сама комиссия съедает треть однопроцентного бюджета.

Отдельного контракта под конвертацию не нужно. Горячий кошелёк держит только накопленные комиссии между конвертациями. Конвертируем часто, сумма всегда маленькая.

### 7.4 Восстановление после сбоя

Сеттлмент детерминирован: из журнала хартбитов всегда получается один и тот же результат. Если воркер умер между расчётом и публикацией, после рестарта он пересчитает то же самое, а `UNIQUE(through_epoch)` не даст опубликовать повторно.

### 7.5 Анти-абьюз

Доказать видимость вкладки невозможно — скрипт шлёт хартбиты не хуже браузера. Это неустранимо и присутствует в прототипе.

Масштаб ограничен линейностью веса: бот с балансом X получает ровно долю, положенную балансу X. Сибил бесполезен — разделение баланса на несколько кошельков даёт тот же суммарный вес.

Поэтому вкладываем минимум: рейт-лимит на аккаунт и IP, одна активная сессия на кошелёк.

### 7.6 Watchdog

Задержка активации корня имеет смысл только вместе с автоматической проверкой — иначе 5 минут окна проходят впустую.

Watchdog после каждой публикации независимо пересчитывает корень из журнала хартбитов и сверяет с опубликованным. При расхождении — немедленный `pause()` и алерт.

Это дёшево, потому что сеттлмент детерминирован: пересчёт есть повторный вызов той же чистой функции. Watchdog не нуждается в отдельной инфраструктуре и живёт в том же процессе, но с отдельным путём кода.

## 8. Тестирование

| Слой | Инструмент |
|---|---|
| Чистые функции | юнит + property-тесты на сгенерированных сценариях |
| Контракт | Foundry, включая форк Robinhood Chain mainnet |
| Интеграция | форк: реальные TSLA и DEX, ненастоящие деньги |

### Обязательные инварианты

1. `totalAllocated - totalClaimed <= balanceOf(vault)` — всегда
2. `cumulative[a]` монотонно не убывает
3. сумма аллокаций <= сумма купленного (пыль не теряется)
4. сумма клеймов == сумма аллокаций при полном клейме всех
5. при `totalWeight == 0` резерв не меняется

## 9. Последовательность запуска

1. Деплой `RewardVault`, **верификация исходника** на Blockscout
2. Предзаряд вольта TSLA
3. `maxAllocationIncreasePerRoot` выставлен низко
4. Запуск токена на лаунчпаде
5. Открытие майнинга в режиме **dry-run**: хартбиты принимаются и пишутся в журнал, корни считаются и логируются, но не публикуются
6. Сверка расчётов на реальных данных
7. Переход к публикации; первый корень покрывает **все эпохи с момента открытия майнинга**
8. Подъём потолка по мере накопления доверия

Пункт 1 предшествует пункту 4 намеренно: контракт должен быть открыт для проверки до того, как участники понесут деньги.

Dry-run стоит **после** запуска токена, а не до: без держателей токена майнеров нет и проверять нечего. Участники при этом ничего не теряют — сеттлмент детерминирован и считается из журнала хартбитов задним числом, поэтому первый реальный корень выплачивает за весь период dry-run.

## 10. Параметры к утверждению

Требуют решения заказчика до запуска. Предложенные значения — стартовая точка, не финал.

| Параметр | Предложение | Комментарий |
|---|---|---|
| Предзаряд вольта | ~5 дневных притоков | выводится из §4; при неизвестном притоке — от желаемой выплаты первого дня |
| `MIN_BALANCE` | 100 000 токенов | как в прототипе |
| Эмиссия токена | 1 000 000 000 | как в прототипе |
| Доля проекта с оборота | задаётся лаунчпадом, не нами | **действие:** выяснить фактическую ставку creator fee выбранного лаунчпада до запуска и подставить в расчёт притока. У прототипа модель 3% трейдер / 2% проект |
| `maxAllocationIncreasePerRoot` | 2x ожидаемого релиза эпохи | **основная** защита от злого корня |
| `CLAIM_DELAY` | 300 с (одна эпоха) | лаг активного корня; см. оговорку ниже |
| Лимит проскальзывания свопа | **2%** | тир пула 0.3% съедает треть однопроцентного бюджета; глубина проверена |
| Порог конвертации | эквивалент $10 | подтверждён замером: покупка на $10 — 0.79% WETH-стороны пула |

### Оговорка про `CLAIM_DELAY`

Задержка даёт всего 5 минут на реакцию и **сама по себе почти ничего не
защищает** — человек в это время обычно спит. Реально работают две другие
вещи: `maxAllocationIncreasePerRoot`, который ограничивает ущерб без
участия человека, и watchdog (§7.6).

Не следует считать задержку самостоятельной мерой безопасности.

## 12. Известные ограничения

Фиксируются осознанно, компенсации не требуют или не имеют.

1. **Видимость вкладки непроверяема.** См. §7.5. Неустранимо.
2. **Сервер — единственный оракул учёта.** Внешней верификации нет. Ончейн ограничен ущерб, но не проверяема корректность.
3. **Одиночный админ-ключ.** Компрометация или потеря кладёт проект. Компенсация — холодное хранение и ончейн-инварианты.
4. **Контракт не аудирован.** Компенсация — минимальная поверхность, OpenZeppelin, инварианты, форк-тесты, staged rollout.
5. **Доход зависит от торгового оборота собственного токена.** Дрип растягивает выплаты, но не создаёт доход при мёртвом обороте.
6. **Непрерывность работы сервера обязательна.** Простой = потерянный заработок участников за это время.

### Правило коммуникации

Публичные материалы не делают ложных утверждений о статусе деплоя, аудита и объёмах. Прототип публикует «contract not deployed yet» при живом торгуемом токене — этот класс ошибок недопустим.
